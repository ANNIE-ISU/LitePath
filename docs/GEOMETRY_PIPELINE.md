# ANNIE Geometry Pipeline

## File Formats and Their Roles

| File | Format | Role |
|---|---|---|
| `InnerStructure.gdml` / `PHASE2_INNER_STRUCTURE.gdml` | GDML (XML) | Original disconnected triangle soup (laser scan). |
| `PHASE2_INNER_STRUCTURE_closed.gdml` | GDML (XML) | Closed contiguous surface mesh (vertex-deduplicated, no boundary edges). Primary geometry for raytracing. |
| `PMTPositions_Scan.txt` | TSV | 132 PMT positions in WCSim scan coordinates. Preferred PMT source. |
| `F10091903_-.step` | STEP AP242 | Full CAD assembly; fallback for PMT/LAPPD positions when no scan file is available. |
| `component_manifest.json` | JSON | Cached output of STEP parser — avoids re-parsing the 196K-line STEP file. |
| `FullTankPMTGeometry_WCSim.csv` | CSV | Human-readable WCSim PMT geometry table (not used by the code). |
| `*.stl` | Binary STL | Generated by `gen_stl.py` / `gen_combined_stl.py` for offline rendering or 3D printing. |
| `*.html` | HTML+JS | Self-contained Three.js visualizations generated by `gen_viz.py`. |

## Coordinate Frames

There are four distinct coordinate frames. The three-stage transform from scan file to raytracing geometry is the trickiest part to get right.

### 1. WCSim Scan Frame

Unit: **cm**.  The raw PMT position file (`PMTPositions_Scan.txt`) lives here.

| Axis | Description |
|---|---|
| scan\_X | horizontal across the detector |
| scan\_Y | vertical (upward in WCSim) |
| scan\_Z | beam axis (downstream = +Z) |

The file has 9 tab-separated columns:
```
TubeID  panel_nr  scan_x  scan_y  scan_z  dirx  diry  dirz  pmt_type
```

**Important:** The `dirx, diry, dirz` columns are **not used** by the raytracer. Directions are assigned purely from the panel number and PMT type, matching WCSim's behaviour.

### 2. WCSim Water-Tank Frame

Unit: **mm**.  Converted from the scan frame by `pmt_loader._scan_to_tank()`.

| Axis | Formula | Description |
|---|---|---|
| X\_w | `scan_x * 10` | horizontal (same orientation as scan X) |
| Y\_w | `(168.1 - scan_z) * 10` | beam axis (scan Z is swapped) |
| Z\_w | `(scan_y + 14.45) * 10` | vertical (scan Y becomes vertical) |

Constants:
- **168.1 cm** — beam centre Z-position in scan coordinates
- **14.45 cm** — vertical offset between scan and WCSim frames

### 3. Structure Rest Frame (GDML Frame)

Unit: **mm**.  The inner structure GDML mesh lives here.  The transformation from the water-tank frame reverses WCSim's Geant4 placement:

```
Placement: rotateZ(+157.5°), translate(0, 0, -½·WCLength)
```

To get back to the structure frame:

```
P_s = Rz(-157.5°) · P_w  +  (0, 0, +½·WCLength)
```

where `WCLength = WCIDHeight = 3960 mm`.  In code (`pmt_loader._tank_to_structure`):

```python
x_s = x_w · cos(-157.5°) - y_w · sin(-157.5°)
y_s = x_w · sin(-157.5°) + y_w · cos(-157.5°)
z_s = z_w + 1980
```

The GDML mesh itself uses **Z-up** (X horizontal, Y horizontal, Z vertical) and is **already in this frame** — no coordinate transformation is applied to the mesh vertices.

An optional `--z-offset` (mm) can be added to Z_s after the transform. This exists because some GDML versions use different Z origins than the PMT scan file.

### 4. Three.js Frame (Visualization)

Three.js uses **Y-up** (X horizontal, Y vertical, Z horizontal).  The offline HTML visualizations (`gen_viz.py`) swap Y ↔ Z on all positions:

```javascript
const t = p[1]; p[1] = p[2]; p[2] = t;
```

The interactive `viz_server.py` frontend does **not** perform this swap — it renders the geometry as-is with Z vertical and positions the camera along all three axes.

## Parsers in Detail

### `gdml_parser.py` — GDML Mesh

Uses `lxml` to parse `<position>` and `<triangular>` elements.  Vertex names follow the pattern `inner_structure.stl_vNNNN`; the parser strips the prefix and uses the numeric index directly.  Returns `(vertices: float32[N,3], triangles: int32[M,3])`.

### `pmt_loader.py` — WCSim PMT Scan File

Applies the three-stage transform described above.  Also assigns per-PMT radii and directions:

| Type | Panel | Direction | Radius |
|---|---|---|---|
| LUX | 0 (bottom) | `(0,0,+1)` | 127.0 mm |
| ETEL | 9 (top) | `(0,0,-1)` | 139.7 mm |
| Hamamatsu | 1-8 (barrel) | radially inward | 101.6 mm |
| Watchman | 1-8 (barrel) | radially inward | 127.0 mm |
| Watchboy | 1-8 (barrel) | radially inward | 127.0 mm |

### `step_parser.py` — STEP CAD Assembly

Uses `cadquery` (OpenCASCADE) to import the STEP file.  Classifies every solid by volume into PMT perches (~41872 mm³), PMT housings (6-12×10⁶ mm³), LAPPD modules (~112050 mm³), inner panels, and the tank bounding box.  Output is a `ComponentManifest` with PMT centers, LAPPD candidates, and tank bounds.

Because STEP parsing is slow (10-60 s), the manifest can be cached to JSON with the `extract-manifest` CLI command.

## Assembly: `build_geometry()` in `geometry/build.py`

The `Geometry` dataclass holds everything the raytracer needs:

```
Geometry
├── mesh_vertices:   float32[N,3]    — triangulated structure (from GDML)
├── mesh_triangles:  int32[M,3]      — triangle index list
├── pmt_centers:     float32[P,3]    — PMT sphere centres
├── pmt_radii:       float32[P]      — per-PMT radius
├── lappd_data:      float32[L,7]    — [cx,cy,cz, nx,ny,nz, half_size]
├── tank_radius:     float           — cylinder radius (mm)
├── tank_z_min:      float           — cylinder bottom Z
└── tank_z_max:      float           — cylinder top Z
```

PMT data is loaded from the **first available** source:

1. **`--pmt-csv`** (preferred) — `pmt_loader.load_pmts()` applies the full scan→tank→structure transform.
2. **`--manifest`** (cached JSON) — uses PMT centres directly from the manifest (already in structure frame).
3. **`--step`** (raw STEP file) — parses the CAD fresh, extracts PMT housing centres.

LAPPD sources come from the manifest or STEP.  Default indices: `[5, 25, 34]` (three LAPPDs at diverse Z and azimuthal positions).  Each LAPPD normal points radially inward.

Tank bounds come from the manifest or fall back to `radius=1264 mm, z=[19, 3861] mm`.

## Ray Tracing

The `trace_kernel` (Taichi GPU) traces rays against four geometry types:

| CID | Object | Algorithm |
|---|---|---|
| 1 | Triangle mesh | Möller-Trumbore |
| 2 | PMT spheres | Quadratic sphere intersection |
| 3 | LAPPD rectangles | Plane + local UV bounds |
| 4 | Tank wall | Infinite cylinder clipped to `[z_min, z_max]` |

All normals point **inward** (toward detector centre).

`trace_cherenkov()` combines `cherenkov.py` (Cherenkov photon generator, angle=0.73 rad ≈ 42°) with the trace kernel and returns per-PMT hit counts + structure hit positions.

## Visualization

The `viz_server.py` uses the **exact same `Geometry` object** as the raytracer, served via HTTP:

- `/api/mesh/verts` — raw float32 binary of all vertex positions
- `/api/mesh/tris` — raw int32 binary of all triangle indices
- `/api/pmts` — JSON with centres, radii, and types
- `/api/trace` — runs `trace_cherenkov()` server-side and returns hit data

The frontend (Three.js) builds a non-indexed `BufferGeometry` from the mesh data (the indexed path has a rendering quirk with this particular mesh), applies `MeshStandardMaterial` with `DoubleSide`, and lights the scene with an ambient + spotlight (Cherenkov-angle-matched) pair.  The spotlight position follows the muon vertex in real time.

## Gotchas

1. **Z-offset mismatch** — Different GDML versions may have different Z origins vs the PMT scan file.  Adjust with `--z-offset`.
2. **STEP parser volume thresholds** — The hardcoded volumes (41872, 112050) in `step_parser.py` depend on the specific CAD revision and may need updating.
3. **Indexed geometry rendering** — The GDML mesh renders as wireframe but not as a solid indexed `BufferGeometry` in Three.js.  The workaround is to flatten to non-indexed geometry.
4. **No WCSim parser exists** — PMT positions come from the scan file or STEP CAD, not from WCSim output directly.
5. **Tank walls in raytracing are an infinite cylinder without end caps** — rays above/below `[z_min, z_max]` miss entirely.
6. **The cumulative JSON manifest is ~134K lines** — it stores every solid from the STEP file.  Consider trimming for production.
